# Task 3.4 - The new prompt appears at once after a cd

## Summary
Fixed. After a `cd` line, the prompt of the folder it moved to now appears in one frame at full opacity, 300 ms after the last `cd` character, and the first character of `tree` follows 101 to 156 ms later. Before, that prompt faded in over about 14 frames starting at opacity 0.11, and the first character of `tree` was typed 16 to 31 ms before the prompt was visible. The bug was only on folder pages that start with a `cd` (every route in step 2 that ends on a folder page). The file page's `cat` line after a `cd` already appeared at once. The tree rows, the prompt after the tree and the footnote still fade over 250 ms. Minimal mode and all other checks are unchanged.

## Output
- Branch `fix/cd-prompt-instant`, one commit on top of `cd29e78`: `fc727e8 fix: show the prompt at once after a cd, then type the command`. It changes `index.html` only, 8 lines in `buildTreePage`, no trailer lines, not pushed. The worktree is clean.
- The change: the line after a `cd` is no longer created with `hidden(...)`, which added the `term-fade` class (and its 250 ms opacity transition). It is created with a plain `style.opacity = '0'` in animated mode, and the existing `revealFn(cmd, true)` at `treeAt` sets it to 1, which with no `term-fade` class is instant. The first character of `tree` is now typed at `treeAt` plus one typing interval (`TYPE_MIN_MS` plus a random part of `TYPE_MAX_MS - TYPE_MIN_MS`), when a `cd` came first. The no-`cd` case (same folder) is unchanged: `tree` types from the start.
- A side effect: the tree rows and everything after them start one typing interval later (90 to 170 ms) after a `cd`, because they are timed from the end of `tree`.
- `tools/prompt-timing.mjs` (local only): the sampler now also reads each line's computed opacity on every animation frame and every DOM change, records the first sample at which the line is visible and its opacity then, and checks lines after a `cd` for opacity 1 in the first visible frame, the 300 ms pause after the last `cd` character, and the first command character 70 to 190 ms after the prompt is visible. New cases: navbar from the root and from another folder, Back, Forward, a typed address, the footnote's `cd ..` (twice), the root item with `cd ..` and with `cd ~`, and a direct load of a folder. `tools/README.md` has the new description.

## Important Findings
- **The `cd` line itself starts typing in the same frame as its prompt.** On a folder page, the `cd` line's prompt is in the page from the first frame at opacity 1, and the first `cd` character is typed 0.5 to 11 ms later, not an interval later. The same happens for the error page's `cd nope/` line (0.5 to 1 ms), and for the `tree` line when no `cd` came first (a folder page reached from a file in the same folder). This is the pattern Follow-up 01 fixed on file pages. It is outside this Task, which covers the prompt after a `cd`, so I did not change it. It needs a follow-up if the User wants an interval after those prompts too. `prompt-timing.mjs` reports it as a skipped check and does not count it.
- **The landing's second prompt fades.** On the landing, the prompt before `tree` (after `whoami`'s output) is revealed with the 250 ms fade, first visible at opacity 0.11, and `tree` types 300 ms after the reveal starts. It follows output, not a `cd`, and the Task said to leave prompts alone unless they were after a `cd`, so I did not change it. The User's rule (machine output appears at once) would cover it. Direct load of any page plays this landing first.
- **The file page's last prompt and the tree's last prompt** still fade, as the Task allows (`treePrompt`, and the file page's end prompt, which is built the same way).
- **Timing shift.** Because `tree` now starts one interval later, the rows and the final prompt and footnote after a `cd` all come 90 to 170 ms later than before.
- `tools/` is still untracked in the root checkout.
